# Index.ets 产品协调职责优化方案

日期：2026-10-08。状态：首轮已实施，包含脚本注册、系统能力适配及搜索业务试点；其余迁移阶段待实施。详情见 reviews/INDEX_COORDINATION_REFACTOR_20261008.md。

建议沿用现有三层架构，将 Index 收敛为应用组合入口：持有稳定的 UI/Store 实例、组合页面、转交生命周期和用户意图。产品导航与会话编排留在 entry 的专用对象中，单一业务的读取、结果校验和状态提交回到所属 feature。按完整业务链逐步迁移，先保持行为等价，再简化内部状态。

## 1. 当前基线与问题

制定方案时 `entry/src/main/ets/pages/Index.ets` 有 9,106 行；已持有七个 `@State` 特性 Store，业务脚本、页面、缓存及原生传输也已有明确模块归属。因此，这轮重点是迁移仍在入口内的行为和副作用，而非重新分包或再复制一组状态。

| 当前职责与源码位置 | 问题 | 建议归属 |
| --- | --- | --- |
| `aboutToAppear` / `aboutToDisappear`，336 / 485 行 | 桥接绑定、网络诊断、导航判定和业务回调集中维护 | entry 生命周期与桥接绑定对象 |
| `updateAuthState` / `resetAuthenticatedContent`，837 / 765 行 | 登录证据处理与多个特性的清理相互交织 | entry 会话协调器；特性提供清理方法 |
| `selectNativeRootTab` / `requestRootPage` / `ensureRootActionContext`，2865 / 3018 / 3121 行 | 原生展示、后台文档读取与业务操作就绪共享大量标记 | entry 导航状态和根页上下文协调器 |
| `updateHome` / `updateSearch` / `updateInbox` / `updateProfile` / `updateBoard` / `updateDetail`，3665 / 2257 / 1577 / 5221 / 4967 / 6201 行 | 业务快照校验、分页合并、错误处理及 Store 提交仍由入口执行 | 所属 feature 的流程控制器和 Store 方法 |
| 首页磁盘缓存及离线标记，3275 行起 | 首页缓存策略、账号隔离及应用认证边界混在一起 | feature_home 缓存服务；认证决策留 entry |
| `handlePostResult`、标题回写，6640 / 6153 / 6181 行 | 单业务结果直接更新多个 Store | feature_pin 产出已确认结果；entry 显式分发 |
| 分享与更多面板 Builder，7715 / 7888 行 | 入口仍包含业务面板行布局和呈现规则 | feature_pin/components |
| `onBackPress`，7576 行 | 发布、编辑、图片、聊天、设置、Sheet 和路由返回揉在同一分支链 | entry 返回协调器；各流程提供消费返回能力 |
| Web 挂载、注入与事件，8490 行起 | 会话容器组合和事件处理难以单独检查 | Web 节点先保留在 Index；注入描述与事件逻辑迁入 entry/app |

例如 `updateHome` 会读取搜索 Store 的标题记录和 Pin Store 的已确认收藏。迁移时应将这一跨特性补充作为 entry 提供的受限呈现输入，不能让 feature_home 直接引用其他 feature。

当前首读行为以源码和 `NATIVE_UI_DEVELOPMENT_NOTES.md` 第 5 行为准：底栏点击只切换原生画面；空根页真正可见后，由 `onRootPageVisible` 延后 80ms 发起首次读取。部分架构说明仍描述为无快照时等待手动重试，实施前应对齐文档，不能把历史描述带入新实现。

## 2. 目标结构与所有权

建议新增以下对象，文件名可在实施中按现有命名调整；这些是目标职责，不是已经存在的能力。

```text
entry/src/main/ets/
  pages/Index.ets                  稳定实例、ArkUI 页面树、事件转交
  app/
    PinWebNavigationState.ets      展示根页、子层、来源及导航代次
    PinWebNavigationCoordinator.ets 根页切换、子页打开和返回目标
    PinWebRootContextCoordinator.ets 首次读取、刷新及操作上下文准备
    PinWebSessionCoordinator.ets   认证状态转换、账号变化及失效事务
    PinWebBridgeBindings.ets       Proxy 回调绑定、路由与解绑
    PinWebScriptRegistry.ets       当前脚本顺序、开关和传输适配
    PinWebPageLifecycle.ets        前后台、销毁及清理编排
    PinWebBusinessResults.ets      已确认跨特性结果的显式分发
    PinWebSystemActions.ets        文件保存、剪贴板、外部应用等适配

feature_*/src/main/ets/
  controllers/                    业务读取、消息验收和流程推进
  stores/                         可观察状态、提交及清理方法
  services/                       原有 API/桥接脚本、缓存及业务服务
  models/                         业务合同与需要注入的能力接口
  components/                     页面与业务面板
```

文件按迁移阶段实际需要创建，不预先创建空类。帖子模块按详情读取、分享、帖子操作等完整流程拆控制器，避免一个 Pin 控制器再次集中所有职责。

- **Index 继续持有七个 Store。** 协调器和流程控制器注入同一实例，子组件接收现有快照或状态。根页切换和显示恢复不重建 Store，也不新增兼容 getter/setter。
- **导航展示状态只有一个写入入口。** Index 以 `@State` 持有 `@Observed` 导航对象，由导航协调器修改；特性只发出导航意图，不直接设置根 Tab 或全局页面地址。
- **真实文档上下文由会话协调器管理。** 当前控制器地址、文档 epoch、账号范围及认证证据不能由展示路由推导。真实控制器与 Cookie 适配不下放给特性。
- **业务就绪由所属特性确认。** 保留 `interactionReady`、输入就绪与 `actionsReady` 的差别；会话协调器认证成功不能直接把所有特性的操作门禁设为就绪。
- **每种业务状态由所属控制器/Store 写入。** 产品层调用 `resetForSessionChange`、`restorePresentation`、`applyConfirmedPinChange` 等明确方法，逐步替代散落的直接字段赋值。
- **跨特性结果留在 entry。** 例如已确认收藏、标题编辑、发布结果，由产品结果分发对象调用有关特性方法。事件携带有界业务字段及有效性上下文，不携带凭据。

依赖保持 `entry → feature_* → common_*`。特性所需脚本执行、上下文准备、系统操作和导航能力，使用该特性导出的明确接口，由 entry 实现并注入。特性不能导入 entry 的接口文件，也不把 Pin、图板、根页等产品合同塞入公共层。

控制器不得持有整个 Index，也不得接收可以任意访问所有状态的宿主对象。跨对象调用通过显式方法和回调连接，不引入全局事件总线、依赖注入框架或仅转发原有脚本的空 Repository。

## 3. 三条核心流程的迁移方式

### 根页：展示、首次读取、操作准备

1. 底栏意图进入导航协调器，完成本地状态切换、旧意图失效及展示恢复，调用同一 `HdsTabsController.changeIndex`。该调用链不派发请求、不执行 Web 导航。
2. 根页可见事件进入根页上下文协调器。仍按现有 80ms 延后和选中页代次校验，仅无快照、无在途读取、无错误且已认证时执行首次读取；正常空快照属于已加载状态。
3. 刷新、重试或已接入业务操作显式申请上下文。保留请求合并、超时、真实地址检查及切页取消；准备成功后重新读取当前操作会话，不消费缓存操作标识。
4. 页内分页、预取和媒体继续使用所属业务的现有就绪与可见性门禁。缓存恢复不会自动开启这些能力。

第一轮只迁移原有判定及 token；在行为对比通过后，才考虑将等待循环改为可取消的就绪通知，避免同时更改导航架构和时序。

### 桥接结果：通用上下文与业务验收分离

`Proxy 回调 → 产品上下文检查 → 特性消息解析/校验 → Store 提交 → 必要的产品结果分发`。

桥接绑定对象负责绑定、解绑和产品会话边界；特性控制器负责原有业务响应、session、目标身份、分类、分页及操作代次检查。原始脚本的请求构造与数据映射继续放在原有 services，不在本轮改写接口合同。

当前各消息合同的 epoch、地址和 session 字段并不应假定完全一致。先逐条保留现有校验；只有业务链验证通过后才补齐合同，不能用一个新通用门禁替代原来的完整地址、当前 Pin 和迟到响应检查。上下文至少在异步派发前及返回提交前重新验证。

`PinWebShareBridge` 虽然名称带 Share，当前实际承担多个业务 Proxy。先保留网页 Proxy 名称和 methodList，内部路由到明确处理器；改名与协议版本化作为独立后续工作。

### 会话变化、生命周期与返回

会话失效首先提升会话/导航/业务任务代次，使旧回调不可提交，再取消请求与等待，关闭面板和子层，由各特性清理展示、缓存和操作标识，最后进入登录展示。清理方法必须幂等，失败或重复调用不恢复旧状态。

账号切换、明确登出、后台暂停和页面销毁采用分别定义的策略：账号切换清理展示内存并切换磁盘分区；明确登出/会话失效按现有合同清理持久缓存；后台保留页面与 ArkWeb 会话并暂停读取/媒体；销毁解除绑定并释放任务。普通网络失败不能被归并为会话失效。

复用现有 `PinWebTaskRegistry` 为页面、业务控制器或流程提供独立任务作用域。定时器、订阅、请求归属及等待都随对应作用域清理；Promise 即便不能主动中断，也必须在恢复执行后检查代次。

返回协调器保留当前 `onBackPress` 的实际优先级和忙碌处理：发布与图片/资料面板、设置/聊天、编辑内层或各 Sheet、子页、根页系统返回。先按现状建立行为表，再收敛为每个流程的 `tryHandleBack`，不能直接改成一个丢失编辑内层和重复返回保护的通用栈。HDS 标题返回、系统返回和网页返回意图最终进入同一产品入口。

## 4. 建议实施顺序

| 阶段 | 实施范围 | 完成标准 |
| --- | --- | --- |
| 0：建立基线 | 列出状态写入点、Proxy 合同、脚本顺序、返回优先级；对齐首读文档；记录新版设备基线 | 当前行为表和静态/构建/设备证据分别留存；识别直接提取 Index 方法的测试 |
| 1：提取组合辅助对象 | 先抽脚本注册表、系统能力适配、诊断辅助；保留 Web 和四个 TabContent 在原页面树位置 | 注入顺序、开关、调用结果和 Web 实例身份保持；对应检查通过 |
| 2：闭环迁移单个根页 | 优先搜索或收件箱，迁移消息验收、分页、刷新、输入/分段流程及清理 | Index 对该业务只转交事件；特性独立验收消息并更新同一 Store；关联返回/操作检查通过 |
| 3：复制已验证模式 | 迁移首页、资料、图板、设置；首页缓存服务接收当前账号范围并返回候选快照，由 entry 决定认证/离线展示 | 四根页快照、正常空状态、滚动、刷新及账号隔离保持；业务数据不再由 Index 解析 |
| 4：迁移复杂帖子流程 | 分别迁移详情读取/预取移交、分享、收藏/编辑/评论及已确认结果分发；业务面板 UI 回到 feature_pin | 连续打开、快速返回、旧响应、读请求移交、面板会话及跨列表更新均符合原合同 |
| 5：收敛产品协调 | 迁移根页上下文、导航/返回、会话清理和生命周期；统一产品状态写入入口 | Index 只组合页面、持有实例和转交事件；无全量宿主引用；销毁无旧回调写入 |

每个阶段拆成可单独验收的改动。涉及抽取的业务链，应同时迁移输入入口、结果处理、状态写入、取消/清理和检查脚本；避免只把一个方法移走，却长期保留两处共同写状态。

单根页试点推荐搜索或收件箱，是因为已有专用 Store、接口脚本和回归入口，可以检验控制器边界；并不意味着它们没有输入、返回或消息写入风险。第一轮保持现有输入草稿、提交查询和取消规则。

## 5. 必须保持的产品与工程合同

- Index 保持唯一 `@Entry`；同一 ArkWeb 维持挂载和完整视口。登录后不可见、不可触摸且不进入无障碍树。
- 四个真实 `TabContent` 保持实例及滚动，根页 `animationDuration(0)`；二级页沿用现有转场、HDS MINI 标题和单层安全区责任。底栏保持 56vp 高、28vp 底距。
- 会话来自当前 ArkWeb；资源属于 Pinterest 网站内部接口，没有原生 OAuth 或独立令牌生命周期。RCP 归 common_network，凭据适配归 common_session，Cookie 不经 Proxy 或另行持久化。
- 网络传输保持当前实现：原生失败不自动回退 Web，业务接口失败不擅自回退 DOM，写请求不自动重放。HTTP 200 不能替代业务响应确认。
- 分享仍统一使用现有 `PinWebNativeShareApiOpen → SHARE_PANEL_BRIDGE_SCRIPT → 原生半模态`。布局提取不得改成系统 ShareKit 或变更平台/联系人合同；实施涉及分享文件时按 AGENTS.md 要求再次查看 AGENTS.md 与 README。
- 未接入业务入口保持无操作；架构迁移不附带启用功能、改开关或清理受保护 backups。
- 沿用当前 ArkUI 状态机制，保持 Store 的真实初始化和可观察更新。本轮不同时升级状态管理版本；禁止在 ArkUI struct 中恢复曾被编译丢弃的兼容访问器。

## 6. 验收与检查脚本迁移

制定方案时运行以下源码基线，均通过：

```text
node scripts/check-module-architecture.cjs
node scripts/check-foundation-architecture.cjs
node scripts/check-page-state-architecture.cjs
```

上述结果是方案编制时的基线。首轮实施后的 46 项检查及未签名 HAP 构建均通过，详细证据与待验收项见 [首轮验收记录](reviews/INDEX_COORDINATION_REFACTOR_20261008.md)。

实施时每轮运行三项基础检查及该业务相关回归。产品协调迁移重点覆盖 `check-native-root-switch`、`check-root-initial-loading`、`check-root-content-actions`、`check-secondary-root-context`、`check-root-tabs-return`、`check-session-startup`、`check-auth-native-shell`、`check-business-lifecycle` 和 `check-cache-consistency`；帖子迁移再覆盖详情打开/离开/返回/文档重绑、预取移交及对应帖子操作检查。

部分脚本直接从 Index 源码提取私有方法或检查具体字段字符串。迁移一个职责时，将测试对象同步切到真实控制器和合同；不要通过拼接源码或扩大 `readLegacySourceFileSync` 投影伪造原位置。现有路径映射用于真实源码归属映射，不能把多个实现当成一份虚拟旧源码。

每轮涉及 ArkTS 运行代码的改动都需构建 entry HAP，并调整/执行 `check-compiled-store-access.cjs`，检查新位置的真实编译产物和仍在 Index 的 Store 初始化/绑定。该脚本当前还依赖 Index 内部字段访问文本，不能在职责迁出后原样当作验收依据。

设备与线上验收使用新安装版本，至少覆盖：

1. 四根页连续切换；有快照恢复、无快照首次读取、正常空快照和失败状态；检查底栏附近点击/滑动。
2. 快速切页后延后任务不读取旧页，后台 Web 回调不抢占当前原生展示。
3. 缓存先显示，操作需等待当前会话；操作准备期间关闭 Sheet/切页后不继续派发。
4. 连续打开不同 Pin、加载未完成即返回、根页返回和嵌套编辑/聊天/设置返回，确认来源和滚动恢复。
5. 前后台往返、明确登出/账号变化、页面销毁，确认旧请求/计时器不再提交，写操作不重放。
6. 浅色/深色、首屏/滚动后的 HDS 标题与安全区；现有分享面板及联系人搜索。

复用 `PageLifecycle`、`RootTabTrace`、`NetworkTrace` 和 `DetailJourney` 观察行为与请求数量。架构拆分本身不作为提速证据；只有同类新版设备场景的首屏、切页、详情打开/返回耗时和请求次数对比才能支持性能结论。

## 7. 收敛指标与回退

主要完成指标：Index 不解析特性业务 JSON、不构造业务请求体、不执行分页合并、不直接维护业务缓存、不包含业务面板行布局；新增单特性操作通常无需修改 Index。跨业务跳转、结果移交及系统能力仍允许修改产品组合层。

Index 可将约 1,500–2,500 行作为最终规模参考，具体取决于保留的页面组合和 Web 声明；不以行数验收。任何新增协调器若仍读取所有 Store、持有整个 Index 或统一处理所有业务消息，说明职责仍未收敛。

当前目录没有可用 Git 仓库，实施前需为每阶段建立独立、可校验的迁移前文件清单/快照；不要把已有历史 backups 当作本轮可直接恢复的版本。每轮验证通过后再迁下一条业务链，失败时只撤回该阶段。历史恢复脚本继续先默认校验，只有用户明确要求回滚并通过校验时才使用 `-Apply`。

第一批“脚本注册表、系统能力适配、搜索流程控制器”已落地。后续依照阶段 3–5 迁移其他特性、复杂帖子流程以及产品上下文/导航/会话协调；真机基线与行为验收需分别补齐。
